제어의 왕복

src/query.ts의 generator loop는 message, turn count, compaction과 pending tool state를 보유한다. src/services/api/claude.ts는 provider event를 내부 content block과 usage·stop reason으로 줄인다.

tool proposal은 toolExecution.ts와 toolOrchestration.ts에서 validation, hook, permission, scheduling을 통과한다. 결과는 protocol-compatible tool_result로 닫혀 다음 model turn에 재주입된다.

흐름을 지키는 불변식

핵심은 함수의 개수가 아니라 짝과 순서다. tool_use에는 tool_result가 필요하고, 실패한 fallback의 결과는 폐기되어야 하며, abort도 미완료 result를 닫아야 한다.

session journal은 append 순서를 보존하고 parent topology를 다시 만들 수 있어야 한다. compaction은 정보를 잃는 대신 무엇을 보존했는지를 명시해야 한다.

전환 다음 두 면은 같은 사용자 요청을 따라가며 각 알고리즘이 언제 소유권을 넘기는지 추적한다.

Concrete example

“설정 파일의 값을 바꿔 줘”라는 요청

예시는 실제 prompt 내용을 재현하지 않고, source에서 관찰된 경계만 사용해 한 요청의 state와 authority 이동을 설명한다.

STEP 01

입력을 분류한다

processUserInputBase는 mode와 origin을 확인하고 media와 attachment를 정규화한다. remote bridge가 허용되지 않은 local command를 보내면 model query 전에 차단한다.

STEP 02

대화 owner가 turn 입력을 만든다

QueryEngine은 external request를 internal message로 바꾸고 session identity와 abort controller가 들어 있는 context를 결합한다.

STEP 03

generator turn을 시작한다

query()는 message와 ToolUseContext를 받고 model stream을 연다. turnCount와 recovery budget은 이 실행이 무한히 반복되지 않게 한다.

STEP 04

partial stream을 내부 block으로 줄인다

content block의 index와 type을 검증하며 delta를 누적한다. file edit tool_use가 완성되면 아직 외부 파일은 바뀌지 않았다.

STEP 05

효과를 허가할 수 있는지 판단한다

tool lookup, schema validation, pre-hook, permission을 통과한 요청만 executor로 간다. denial도 protocol-compatible tool_result로 돌아간다.

계속 다음 면은 file edit의 stale check와 commit point, tool_result closure, transcript append, resume 가능 상태까지 이어진다.

TRACE-E2E · CONTINUED · STEPS 06–10

효과의 완료와 다음 turn의 시작

현재 상태: tool identity와 input은 검증되었고 permission은 allow다. 아직 성공을 주장할 수 없으며 filesystem commit과 결과 closure가 남아 있다.

STEP 06

읽었던 파일이 아직 같은지 확인한다

FileEditTool은 expected string과 match cardinality를 검사하고 동기적으로 다시 읽는다. stale이면 write 전에 실패한다.

STEP 07

temporary file을 flush하고 rename을 시도한다

mode와 symlink behavior를 가능한 범위에서 보존한다. atomic replace가 실패하면 flushed direct write로 fallback하지만 cleanup은 best effort다.

STEP 08

결과를 tool_result로 닫는다

성공·실패·거부·abort는 서로 다른 의미를 유지한 채 result가 된다. turn loop는 누락된 result가 있으면 합성해 pairing invariant를 회복한다.

STEP 09

journal에 순서대로 append한다

message UUID와 parent cursor를 연결하고 per-file queue가 JSONL line 순서를 보존한다. 이 기록은 다음 model request와 resume의 근거다.

STEP 10

다음 turn 또는 복구 경로를 선택한다

정상 경로라면 result를 다시 model context로 넣는다. 재개라면 parent graph, compact segment, orphan sibling을 repair한 뒤 bounded chain을 구성한다.

실행을 이해하는 질문

trigger가 무엇인지, state를 누가 보유하는지, 어떤 transition이 authority를 넘기는지, failure가 result인지 abort인지, recovery가 retry인지 repair인지 묻는다.

특히 tool_use/tool_result closure, bounded retry, ordered transcript, stale-state rejection은 서로 다른 파일에 있어도 같은 품질 원칙을 공유한다.

구조를 바꾸는 질문

directory보다 contract seam을 먼저 찾고, behavior fixture와 differential trace를 만든다. 의미 모듈 후보는 소유권 선언이 아니라 이 질문을 분리하기 위한 지도다.

다음 단계는 큰 이동이 아니라 하나의 pure policy, 하나의 adapter, 하나의 vertical slice를 증거와 함께 바꾸는 일이다.
