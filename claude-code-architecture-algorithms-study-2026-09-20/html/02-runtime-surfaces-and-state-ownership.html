    ALGORITHM A03 · 설명의 보장 경계

    이 구현이 지키려는 조건과, 설명이 멈춰야 하는 조건

    여기서 불변조건은 형식적 증명의 결론이 아니다. 어느 전이가 의도한 의미를 보존했는지 읽고, 어떤 반례를 넣어 설명의 범위를 확인할지를 정하는 학습 도구다.

    전이 전후에 확인할 조건

    • 상태·계산 모델의 질문으로 읽기. 하나의 실행에서 정확히 한 top-level route만 선택된다.
    • 구성·변형·성능의 질문으로 읽기. fast path는 불필요한 module side effect를 평가하지 않는다.
    • 상태·계산 모델의 질문으로 읽기. feature-excluded path는 외부 bundle에서 사라질 수 있다.

    최종 출력만 같아도 중간 identity나 effect가 달라질 수 있으므로, 각 조건을 보존하는 transition을 함께 관찰해야 한다.

    설명의 범위를 드러내는 반례

    • predicate 순서 충돌
    • top-level import의 조기 side effect
    • gate와 runtime policy의 불일치

    이 반례가 나타나면 “알고리즘이 틀렸다”로 끝내지 않고 어떤 state owner와 boundary에서 의미가 갈라졌는지 기록한다.

    OBSERVEDregistry보다 명시적 early return을 택해 startup cost와 DCE 가능성을 우선한다.

    RECOMMENDATIONroute table을 문서화하되 dynamic import와 compile-time literal을 훼손하지 않는 characterization test를 둔다.

    ALGORITHM A03 · effect와 운영

    정상 경로 뒤에 남는 effect와 실패 뒤에 남는 상태를 구분한다

    선택된 route만 자신의 초기화와 event loop lifetime을 시작한다.

    effect가 시작되고 관찰되는 경계

    top-level import가 생기면 선택되지 않은 표면도 초기화 side effect를 만들 수 있다.

    현재 설계가 선택한 trade-off와 비용

    registry보다 명시적 early return을 택해 startup cost와 DCE 가능성을 우선한다. 이 선택의 계산·운영 비용은 인자 수가 작을 때 사실상 O(R), R은 route predicate 수다.로 기술되지만, 비용 표기만으로 중복 effect나 부분 상태의 의미가 해결되지는 않는다.

    실패·중단 뒤에 실제로 남을 수 있는 상태

    겹치는 predicate나 gate/policy 불일치는 잘못된 owner를 선택하거나 사용 불가능한 route를 노출한다. 이때 함께 대입할 반례는 predicate 순서 충돌, top-level import의 조기 side effect, 그리고 gate와 runtime policy의 불일치이다. 이들을 모두 하나의 “실패”로 접으면 retry와 cleanup이 무엇을 이어받아야 하는지 알 수 없다.

    관측이 다음 판단에 답하게 하는 법
