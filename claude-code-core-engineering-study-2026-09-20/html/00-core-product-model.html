CORE THESIS02

이 프로젝트는 “대화형 코드 변경 런타임”이다

채팅은 입구다. 제품이 완성해야 하는 일은 불완전한 자연어 요구를 저장소 문맥에 결합하고, 모델의 행동 제안을 검증된 효과로 실행하며, 결과를 다음 추론과 재개 가능한 세션에 되돌리는 것이다.

Context → Proposal → Authorized Effect → Observation → Reconciliation

이 다섯 항 중 하나라도 빠지면 제품은 답변기는 될 수 있어도 코딩 에이전트가 되지 못한다. Context가 틀리면 엉뚱한 파일을 고치고, Effect가 통제되지 않으면 안전하지 않으며, Reconciliation이 없으면 다음 turn과 resume가 거짓 상태를 본다.

핵심 단위는 “메시지”가 아니라 코드 변경 작업메시지·스트림·UI는 작업의 상태를 운반하는 표현이다. 설계 판단은 최종 저장소 효과와 그 정합성에서 역산해야 한다.

WORK EXAMPLE05

“함수 이름을 바꾸고 테스트하라”가 요구하는 것

짧은 요청도 실제로는 읽기·판단·쓰기·검증·회복이 결합된 작업이다.

01작업 해석명령/skill/일반 prompt를 구분하고 현재 cwd·규칙·선택 영역을 결합한다.
02증거 수집검색과 읽기로 대상·호출자·테스트를 찾고 read state를 만든다.
03변경 제안모델이 Edit/Bash tool_use와 구조화된 입력을 생성한다.
04권한·정합성schema, path, deny rule, read-before-write, stale-write를 검증한다.
05효과 실행파일을 수정하고 LSP·IDE·history·telemetry를 갱신한다.
06재검증·합류테스트 결과를 tool_result로 되돌리고 다음 turn 또는 terminal을 결정한다.

AUTHORITY07

모델 출력은 실행 권한이 아니라 제안이다

모델은 tool 이름과 JSON 입력을 제안한다. 런타임은 존재 확인, schema parsing, 의미 검증, permission, hook, sandbox를 거친 뒤에만 효과를 허용한다.

tool_use비신뢰 제안
→
schema모양 검증
→
validate도메인 제약
→
permission권한 결정
→
call실제 효과
→
tool_result관찰 환류

이 경계는 단순 validation pipeline이 아니다. 실행 전에는 authority를 좁히고, 실행 후에는 결과를 모델이 이해할 protocol message로 변환한다. 따라서 Tool 계약은 모델 API, 보안, runtime, UI를 동시에 잇는 anti-corruption layer다.

TIME08

핵심 난점은 호출 순서보다 시간의 중첩이다

모델 스트림, tool 실행, 사용자 추가 입력, hook, prefetch, transcript write가 동시에 진행된다.

중첩

stream과 tool

tool_use block이 완성되면 모델 응답이 끝나기 전 실행을 시작할 수 있다.

동시성

read 병렬·write 직렬

입력별 isConcurrencySafe 판정으로 순서를 보존한다.

취소

cooperative abort

signal은 요청일 뿐 이미 발생한 외부 효과의 rollback은 아니다.

내구성

write queue와 flush

화면의 완료와 디스크의 완료가 같은 순간이 아니다.

배경지식
이 시스템은 synchronous call stack보다 structured concurrency, optimistic concurrency control, saga/compensation 관점으로 읽을 때 실패 경로가 보인다.

DESIGN12

READING METHOD16

한 vertical slice를 끝까지 읽는다

추천 단위는 “prompt 입력”도 “파일 한 개”도 아니다. 하나의 repository effect가 제안되고 확정되며 저장·복구되는 전 구간이다.

  1. Edit를 고른다: schema와 prompt가 모델에게 무엇을 허용하는지 본다.
  2. validate/checkPermissions에서 read-before-write, deny rule, path normalization을 추적한다.
  3. call에서 critical section, patch, LSP/IDE/history 갱신을 본다.
  4. tool_result가 query state와 다음 API 요청에 어떻게 합류하는지 본다.
  5. abort/fallback/resume에서 같은 effect가 중복되거나 사라지지 않는지 반례를 만든다.
  6. REPL/SDK가 동일 사건을 어떻게 다르게 보여 주는지 비교한다.
완료 조건함수 호출 순서를 말하는 것이 아니라, 어떤 state와 authority가 이동했고 어떤 불변조건이 각 경계에서 보존되었는지 설명할 수 있어야 한다.
