OCC08

Edit는 파일을 lock한 채 모델이 생각하도록 만들지 않는다. 먼저 읽고, 쓰기 직전에 여전히 같은 상태인지 확인한다.

mtime만 믿지 않고 Windows cloud sync/antivirus의 false positive를 content 비교로 보정한다. 이는 version number 대신 timestamp+snapshot을 쓰는 OCC다.

CRITICAL SECTION09

“await를 두지 않는다”가 동시성 설계다

directory 생성과 history backup은 critical section 밖에서 await한다. staleness check와 write 사이에 yield하면 다른 edit가 끼어들 수 있기 때문이다.

핵심 코드 판단
Node의 single thread가 race를 없애 주지 않는다. await는 event loop에 제어를 돌려주므로 check-then-act 사이가 열릴 수 있다. 이 구간은 synchronous read/patch/write로 좁혀져 있다.

다만 이것은 process 내부의 interleaving만 줄인다. 다른 process나 editor가 check 직후 write할 수 있는 TOCTOU 가능성, crash 중간 상태, filesystem atomicity는 별도 문제다.

AbortSignal은 model stream과 tool에 전달되지만 이미 쓴 파일, 보낸 요청, 시작한 process가 자동으로 원상복구되지는 않는다.

전파

정합성

정리

MCP18

MCP는 새 Tool 공급자이지 별도 core가 아니다

외부 server의 tool도 동일한 resolve→schema→permission→call→result 경계를 통과해야 제품 안전성이 유지된다.

MCP가 추가하는 것은 remote transport, server identity, authentication, URL elicitation, metadata, dynamic connection이다. 이것들은 adapter 책임이다. model이 보는 관점에서는 built-in Tool과 유사하지만 runtime은 remote trust와 failure를 더 다뤄야 한다.

REFACTORING19

Tool을 다섯 interface로 찢기 전에 조합점을 설계한다

현재 계약의 문제는 크기 자체보다 서로 다른 consumer가 한 타입을 공유한다는 것이다.

  • identity와 input/output schema는 모든 facet을 묶는 단일 source of truth로 유지한다.
  • headless path는 Presenter를 import하지 않아도 되게 한다.
  • permission과 concurrency classification이 같은 parsed input을 사용하게 한다.
  • compatibility alias와 observer backfill은 adapter로 격리한다.
위험
한 번에 모든 tool을 migration하면 schema/prompt/render drift를 만들기 쉽다. 먼저 adapter로 기존 Tool을 새 facet에 투영하고 contract fixture를 만든 뒤 하나씩 옮긴다.

CONCLUSION21

좋은 effect runtime의 조건

기능 수보다 효과의 해석 가능성과 실패 후 정합성이 중요하다.

  • 모델 input은 실행 전 runtime schema와 현재 상태 검증을 거친다.
  • permission은 tool name이 아니라 구체 입력과 effect를 본다.
  • read-only/concurrency-safe/destructive는 서로 다른 속성으로 유지한다.
