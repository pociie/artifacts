VARIABILITY07

feature gate는 조건문이 아니라 product-line architecture다

AST 기준 feature() 호출이 광범위하며, 일부 모듈은 conditional require로 build output에서 문자열까지 제거한다.

이 환경에서는 “flag off면 실행 안 됨”만으로 부족하다. bun:bundle의 tree-shaking 제약 때문에 feature literal이 어떤 조건식에 등장하는지, gated module을 static import하는지까지 구조에 영향을 준다.

DCE08

dead-code elimination 요구가 module boundary를 만든다

feature-gated string과 import가 외부 build에 남으면 안 되는 경우 dynamic require/import가 사용된다.

일반적인 dependency injection 관점에서는 어색해 보여도, 여기서는 artifact 내용 자체가 acceptance constraint다. 리팩터링 시 static import로 바꾸면 runtime은 같아도 build가 다른 제품이 된다.

배경지식
이것은 Strategy pattern보다 software product line과 conditional compilation 문제다. architecture fitness에는 동작 테스트뿐 아니라 excluded symbol/string 검사도 필요하다.

PHASE A13

1단계: 현재 의미를 trace로 고정한다

코드 이동 전에 한 turn의 사건과 외부 효과를 기록하는 characterization harness가 필요하다.

  1. fixture: text-only success, Read→Edit→Bash, permission deny, user abort, stream fallback, prompt-too-long, resume.
  2. 관측: CoreEvent sequence, tool ids, terminal reason, provider request hash, transcript projection, filesystem diff.
  3. entrypoint: REPL adapter와 SDK adapter가 같은 fixture에서 허용된 차이만 보이는지 비교.
  4. feature: 주요 gate on/off 조합을 pairwise로 선택하고 excluded symbol 검사 포함.
왜 먼저인가
복원 저장소에는 완전한 test suite와 build module이 없다. 새 unit test만 쓰면 현재 암묵 contract를 놓치므로 characterization이 선행되어야 한다.

LIMITS19

이 분석이 말할 수 없는 것

복원본의 구조만으로 실제 조직·테스트·배포 체계를 완전히 알 수 없다.

  • shallow clone은 장기 Git history와 실제 refactor chronology를 제공하지 않는다.
  • README가 밝힌 누락 feature modules 때문에 import graph와 build 결과가 불완전하다.
  • feature() 호출 존재는 현재 사용자 build에서 활성임을 뜻하지 않는다.
  • 주석의 incident 번호와 production 수치는 외부 record 없이 독립 검증할 수 없다.
  • 제안한 target architecture는 교육적 재구성이며 upstream roadmap이 아니다.

이 한계를 유지하면서도 state owner, effect boundary, protocol invariant, 현재 코드의 explicit migration comment는 충분히 학습할 수 있다.

CONCLUSION20

구조 개선의 중심 원칙

이 프로젝트는 복잡해서 계층을 더 만드는 것이 아니라, 외부 효과와 장기 상태를 안전하게 다뤄야 해서 복잡하다.

  • turn semantics를 한 conversation owner로 모은다.
  • model representation, authority, effect, projection, durability를 분리한다.
  • cache·resume·compatibility처럼 bytes와 history에 민감한 계약은 먼저 oracle을 만든다.
  • feature variability를 build/runtime/provider 축으로 명시하고 조합 폭발을 관리한다.
  • 운영 telemetry를 새 구조의 동등성·성능·안전 acceptance에 사용한다.
  • 리팩터링은 파일 이동이 아니라 불변조건의 소유권을 선명하게 만드는 작업이다.
