CORE QUESTION02

왜 채팅 앱이라는 모델이 부족한가

사용자가 보는 화면과 시스템이 책임지는 결과 사이에는 무엇이 있는가?

성립 조건

코딩 에이전트는 텍스트를 생성하는 데서 끝나지 않고 파일·프로세스·세션을 변화시킨다.

이론 렌즈

언어 처리계는 description을 실행 가능한 표현으로 낮추고, 보호계는 subject의 요청을 resource effect 앞에서 중재한다.

코드의 구체화

Tool 계약, schema parse, permission, tool-specific validation, call, result pairing이 모델 출력과 저장소 효과 사이에 놓인다.

깨지는 지점

대화 메시지만 추적하면 stale write, denied effect, partial execution, resume 불일치를 설명하지 못한다.

해석가장 생산적인 모델은 “대화 UI”가 아니라 “모델이 제안한 효과를 통제하여 해석하는 런타임”이다.

EXPLANATION FORM04

한 페이지는 하나의 인과 주장을 완성한다

왜 순서도만으로는 설계를 설명할 수 없는가?

성립 조건 × 이론 렌즈 × 코드 구체화 × 실패 반례 → 설계 의미

실행 순서는 “무엇 다음에 무엇”을 보여 주지만, 왜 경계가 필요한지와 어떤 조건에서 비유가 깨지는지는 보여 주지 않는다. 따라서 본문은 원인과 제약을 먼저 설명하고, 순서는 race·pairing·settlement처럼 시간 자체가 불변조건인 경우에만 사용한다.

독해 규칙코드 이름을 이론 용어로 치환하지 않는다. 유사성을 만드는 관찰과 유사성이 끝나는 한계를 함께 적는다.

CORE MODEL11

다섯 책임이 하나의 코드 변경을 성립시킨다

프로젝트 핵심을 가장 작게 표현하면 무엇인가?

Evidence-bearing Context → Proposed Program → Authorized Effect → Typed Observation → Durable Reconciliation

Context는 단순 token 묶음이 아니라 출처와 순서를 가진 실행 입력이다. Proposed Program은 tool name과 arguments로 표현된다. Effect는 permission과 현재 상태를 통과해야 한다. Observation은 같은 tool id와 결합해야 하며, reconciliation은 다음 turn·transcript·resume가 같은 과거를 보게 한다.

핵심성 판정이 다섯 책임을 직접 소유하거나 그 불변조건을 지지하지 않는 기능은 확장·adapter·projection으로 분류한다.

LIMIT15
