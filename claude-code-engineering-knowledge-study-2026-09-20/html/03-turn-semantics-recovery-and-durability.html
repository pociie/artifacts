PROBLEM FRAME01

turn의 경계는 API response보다 넓다

언제 한 turn이 끝났다고 말할 수 있는가?

성립 조건

한 turn 안에 streaming message, tool proposal, 외부 effect, hook, user abort, transcript write가 섞인다.

이론 렌즈

state machine에서 completion은 transition sequence와 terminal state의 의미로 정의된다.

코드의 구체화

query generator가 중간 event를 yield하고 terminal reason을 return하며 QueryEngine/entrypoint가 후처리한다.

깨지는 지점

HTTP stream 종료만 completion으로 보면 tool effect와 durable history가 아직 합류하지 않았을 수 있다.

해석turn completion은 transport 종료가 아니라 protocol·effect·durability의 settlement 조건이다.

SAGA03

부분 효과는 rollback보다 compensation을 요구한다

왜 실패 후 이전 상태로 돌아간다고 가정할 수 없는가?

성립 조건

파일 write, process spawn, network call은 이미 외부 세계를 바꿀 수 있다.

이론 렌즈

Saga는 long-lived work를 여러 transaction과 compensating action으로 본다.

코드의 구체화

query는 tool failure/abort를 result와 terminal reason으로 합류시키고 후속 recovery를 선택한다.

깨지는 지점

모든 tool에 inverse가 없고, compensation 자체도 실패할 수 있으므로 database saga 구현과 동일하지 않다.

해석Saga 비유의 가치는 “error=zero effect” 가정을 버리고 부분 효과 receipt와 후속 정합화를 요구하는 데 있다.

PAIRING05

tool_use와 tool_result는 protocol상의 괄호다

왜 orphan message가 단순 표시 오류가 아닌가?

성립 조건

provider와 다음 reasoning은 tool proposal과 관찰을 id로 연결해야 한다.

이론 렌즈

well-formed protocol은 open request가 정확히 대응하는 response 또는 명시적 tombstone으로 닫혀야 한다.

코드의 구체화

model error/fallback path가 missing result를 repair하거나 failed attempt의 projection을 제거한다.

깨지는 지점

orphan tool_use는 다음 request를 invalid하게 만들거나 모델이 effect 결과를 잘못 추론하게 한다.

해석pairing은 UI 정리 규칙이 아니라 conversation history의 문법 불변조건이다.

TOMBSTONE06

삭제 표지는 새 데이터가 아니라 실패한 역사를 보존한다

왜 failed attempt를 그냥 배열에서 지우지 않는가?

fallback 때 이전 attempt의 content가 새 provider/model path에 노출되면 중복 proposal이나 invalid pairing이 생길 수 있다. tombstone은 “이 entity가 없었다”가 아니라 “이 projection에서 무효화되었다”는 lineage signal이다.

provenance 관점invalidation event를 남기면 observer와 durable history가 실패 전후 entity를 구분할 수 있다.

FALLBACK07

fallback은 같은 호출을 다른 provider에 다시 보내는 일이 아니다

이미 streaming된 output과 effect가 있다면 무엇이 달라지는가?

성립 조건

첫 attempt가 partial text나 tool proposal을 방출했을 수 있다.

이론 렌즈

retry safety는 operation identity와 effect uncertainty를 보존해야 한다.

코드의 구체화

request/observer projection을 정리하고 cache-related state를 보존하며 recoverable error를 일시 보류한다.

깨지는 지점

첫 attempt의 tool이 실행됐는데 두 번째 attempt가 같은 tool을 다시 제안하면 duplicate effect가 발생한다.

해석fallback policy는 transport availability와 semantic replay safety를 함께 판정해야 한다.

ASYNC GENERATOR08

BACKPRESSURE10

pull protocol도 무한 producer를 자동으로 통제하지 않는다

UI가 느릴 때 어떤 queue가 커지는가?

성립 조건

ABORT11

CONCLUSION19
