VARIABILITY09

feature gate는 if문보다 넓은 제품군 문제다

왜 dynamic import와 excluded symbol 검사가 필요한가?

성립 조건

provider/build/cohort에 따라 포함 가능한 code와 capability가 달라진다.

이론 렌즈

Software Product Line은 commonality와 variability, feature constraint를 모델링한다.

코드의 구체화

feature() call, mode filtering, dynamic module loading이 artifact/runtime variant를 만든다.

깨지는 지점

gate 밖 static import나 문자열이 build artifact에 남으면 runtime false여도 product constraint를 위반한다.

해석feature variability는 code path뿐 아니라 module graph와 produced artifact를 acceptance 대상으로 만든다.

CHARACTERIZATION11

불완전 복원본에서는 기존 의미를 먼저 포획한다

unit test를 더 쓰는 것만으로 왜 부족한가?

성립 조건

완전한 test suite/build module과 missing type source가 없다.

이론 렌즈

characterization은 현재 observable behavior를 migration oracle로 만든다.

코드의 구체화

CoreEvent sequence, effect diff, terminal, journal/resume, request hash를 fixture별로 기록한다.

깨지는 지점

현재 bug까지 무비판적으로 영구화하거나 observer가 behavior를 바꾸면 oracle이 오염된다.

해석characterization은 정답 선언이 아니라 의도적으로 바꿀 차이와 보존할 차이를 분리하는 baseline이다.

CONCLUSION18

진화 가능한 구조는 의미의 이동을 추적할 수 있다

이 권에서 남겨야 할 한 문장은 무엇인가?

리팩터링의 단위는 파일이 아니라 invariant ownership이고, 완료의 증거는 diff가 아니라 실패 scenario에서의 동등성이다.

분포와 주석은 어디를 볼지 알려 주고, 이론은 어떤 반례를 만들지 알려 준다. 최종 구조 판단은 고정된 코드 관찰·quality scenario·검증 가능한 migration seam의 결합에서 나온다.
