CHAPTER 04

Provider 경계에서 의미를 보존한다

서비스 API 코드는 HTTP 호출 래퍼가 아니다. 내부 메시지와 모델별 요청 형식, cache, retry, fallback의 차이를 흡수하는 anti-corruption layer다.

분포 수치는 중요도 점수가 아니다. 이 권이 직접 펼쳐보는 코드 표면의 규모와 언어 메커니즘 밀도를 가늠하기 위한 탐색 표지다.

async *submitMessage는 Promise 하나로는 표현하기 어려운 중간 메시지, tool progress, 최종 결과를 차례로 내보낸다. await는 내부 비동기 작업을 기다리고 yield는 외부 소비자에게 현재까지의 관찰을 넘긴다.

따라서 generator는 단순한 스트리밍 문법이 아니다. producer의 실행이 consumer의 next()에 맞춰 재개되고, 취소·오류·조기 return이 protocol 종료 의미를 갖는다. 영상에서 강조된 generator의 장점은 바로 이 지점에서 프로젝트의 실제 구조와 만난다.

하나의 signal이 여러 비동기 경계를 통과해도 이미 일어난 외부 효과는 되돌아가지 않는다.

하지만 사용자가 중단을 누른 순간 파일 write가 이미 끝났다면 signal은 그 효과를 취소하지 못한다. 따라서 UI의 “중단됨”, query protocol의 종료, 실제 파일 시스템 상태를 같은 것으로 취급하면 안 된다.

취소 설계는 세 질문으로 검토하자. 새 작업 시작을 막는가, 진행 중 I/O에 signal을 전달하는가, 부분 효과 뒤 어떤 결과를 journal에 남기는가. 이 셋이 모여야 사용자가 본 상태와 실제 상태가 다시 합쳐진다.

Provider 경계에서 의미를 보존한다

서비스 API 코드는 HTTP 호출 래퍼가 아니다. 내부 메시지와 모델별 요청 형식, cache, retry, fallback의 차이를 흡수하는 anti-corruption layer다.

내부 메시지와 provider payload를 같은 타입으로 두지 않는 이유

세션이 기억해야 할 사실과 특정 API가 요구하는 직렬화는 수명이 다르다.

내부에는 UI용 메타데이터, transcript 식별자, attachment provenance가 있지만 provider는 정해진 role/content/tool schema만 받는다. API 경계는 이 차이를 지우는 곳이 아니라 의도적으로 변환하는 곳이다.

내부 타입을 provider SDK 타입으로 곧장 사용하면 SDK 업데이트가 세션 저장 형식까지 흔든다. 반대로 변환 함수가 너무 느슨하면 중요한 tool id나 cache marker가 소실된다. 경계의 품질은 필드 수가 아니라 보존해야 할 invariant의 명시성으로 평가해야 한다.

provider를 추가하거나 버전을 올릴 때는 request shape 비교뿐 아니라 stop reason, usage, streaming error가 내부 event로 어떻게 정규화되는지 확인하자.

  1. entrypoints/cli.tsx에서 선택된 실행 모드가 main.tsx의 어느 composition으로 이어지는지 찾는다.
  2. QueryEngine.submitMessage의 config 구조 분해에서 session-level port와 turn-level option을 두 색으로 구분한다.
  3. query.ts에서 model phase와 tool phase를 나누고, 각 경계를 넘는 message id와 tool_use id를 적는다.
  4. abort, permission denial, unknown tool, provider stream failure 네 반례가 어떤 SDK message와 transcript 상태를 남기는지 비교한다.
  5. 리팩터링 seam 하나를 고르고 입력·출력·실패·동등성 oracle을 한 장에 작성한다.
완료의 기준한 turn을 “사용자 → 모델 → 도구 → 모델” 화살표가 아니라 상태·식별자·종료 의미를 가진 protocol로 설명할 수 있으면 된다.
