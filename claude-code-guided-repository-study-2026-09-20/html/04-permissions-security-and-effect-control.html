권한·보안·효과 통제Hooks와 원격 정책은 제어 평면을 확장한다

hook은 확장점이지 자동으로 신뢰된 판정자가 아니다

PreToolUse와 PermissionRequest hook은 input과 decision에 영향을 줄 수 있으므로 출처와 실패 정책이 중요하다.

toolExecution은 hook 결과가 updatedInput과 permission decision을 제공하는 경우를 처리한다. 외부 command hook이 allow를 반환했다고 해서 그 command 자체가 신뢰된 authority인지, advisory인지 설정에 따라 달라질 수 있다.

hook timeout, crash, malformed output에서 fail-open하면 우회가 되고 fail-closed하면 availability가 떨어진다. 모든 hook에 같은 실패 정책을 쓰기보다 effect class와 deployment trust를 고려해야 한다.

hook이 무엇을 보았는지도 privacy surface다. 전체 tool input을 전달하면 secret이 외부 script나 service로 나갈 수 있다.

하나의 위험한 명령에 대한 control stack 검토

각 방어가 무엇을 아는지, 어디에서 실패하는지, 다음 방어가 무엇을 보완하는지 연결한다.

  1. 환경 변수 변경과 redirect를 포함한 compound shell command를 하나 만든다.
  2. schema, bash parser, permission rule, user ask, sandbox, process 실행 단계별 입력을 기록한다.
  3. parser unknown, hook timeout, sandbox unavailable, managed setting stale 네 실패를 각각 삽입한다.
  4. 각 실패에서 fail-open/fail-closed 결과와 사용자에게 보여야 할 설명을 비교한다.
  5. 남는 residual risk 하나를 threat scenario 형식으로 작성한다.
완료의 기준“permission이 있으니 안전하다”가 아니라 여러 control이 서로 다른 실패를 줄이며 남는 위험도 존재한다고 설명할 수 있으면 된다.
