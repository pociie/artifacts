SDK message는 내부 event의 공개 projection이다

외부 caller에게 필요한 정보와 내부 구현 세부를 구분해야 버전 가능한 계약이 된다.

QueryEngine은 internal message와 state를 SDKMessage로 변환해 yield한다. permission denial, usage, partial message 포함 여부처럼 headless consumer에게 필요한 사건이 명시된다.

내부 object를 그대로 노출하면 빠르게 만들 수 있지만 필드 rename 하나가 public break가 된다. 반대로 지나치게 단순한 result만 주면 host가 progress와 control을 구현할 수 없다.

SDK contract를 바꿀 때는 additive field, new union variant, changed ordering을 구분하자. 소비자가 exhaustive switch를 쓸 수 있으므로 새 variant도 호환성 변화다.

server가 광고한 schema와 transport event를 내부 registry와 permission model에 맞춰야 한다.

MCP client/normalization 코드는 server description, tool name, input schema, result content를 내부 형태로 바꾼다. 외부 server가 준 문자열은 신뢰된 코드가 아니므로 이름 충돌과 malformed schema를 다뤄야 한다.

MCP specification이 interoperability를 제공해도 로컬 authority는 따로다. server 연결 성공은 tool 실행 허가가 아니며, resource read와 tool effect의 위험도도 다르다.

새 MCP transport를 추가할 때 protocol mapping과 trust policy를 분리하자. stdio, HTTP, in-process는 인증과 프로세스 경계가 다르지만 내부 Tool contract는 같을 수 있다.

AgentTool은 새 conversation engine을 여는 도구다

prompt 하나를 넘기는 것처럼 보여도 child의 도구, 모델, memory, permission을 다시 구성한다.

AgentTool과 runAgent 코드는 agent definition을 고르고 child context를 만들어 실행한다. parent는 child의 전체 transcript 대신 요약된 result와 progress를 받을 수 있다.

이 중첩은 context isolation과 병렬 탐색을 가능하게 하지만 비용과 authority가 증폭된다. child가 parent보다 넓은 tool set을 갖거나 permission prompt를 띄울 수 없으면 명시적 정책이 필요하다.

새 agent type을 추가할 때 persona보다 capability와 termination을 먼저 정의하자. 설명 문구만 다른 agent는 architecture상 별도 runtime일 이유가 약하다.

Task는 background execution의 lifecycle record다

running, completed, failed, killed 상태가 UI pill보다 더 큰 의미를 가진다.

LocalAgentTask, LocalShellTask, RemoteAgentTask는 서로 다른 executor를 감싸지만 task id와 status, output 위치, stop 동작을 공통으로 제공한다. parent session은 이 상태를 attachment로 다시 context에 넣는다.

background task는 parent turn이 끝난 뒤에도 살아 있을 수 있다. 그래서 process-local object와 session durable reference를 구분해야 한다. 재개 후 running이라고 적힌 task가 실제로 존재하는지도 reconciliation이 필요하다.

task abstraction을 통합할 때 모든 종류를 동일 state machine으로 강제하지 말고 공통 lifecycle과 type-specific effect를 분리하자.

병렬 agent는 결과 수보다 context merge가 어렵다

여러 child가 같은 workspace를 읽고 쓰면 결과의 순서와 충돌을 parent가 해결해야 한다.

AgentTool이 여러 탐색을 동시에 수행하면 읽기 결과는 합치기 쉽지만 코드 변경은 shared-state collision을 만든다. task complete 순서가 논리적 우선순위는 아니다.

따라서 parallelism은 독립성 evidence가 있을 때만 이득이다. read-only 탐색, 별도 worktree, 명시적 ownership이 없으면 빠른 실행이 더 많은 reconciliation 비용을 만든다.

parent prompt에 결과를 단순 연결하면 상충 사실과 stale observation이 섞인다. source agent, revision, observed path를 보존한 merge가 필요하다.

영상의 UI와 generator를 이 축 안에서 읽는다

두 메커니즘은 제품의 전부가 아니라 runtime과 사람·host를 잇는 시간적 표현이다.

async generator 영상의 핵심은 중단 가능한 progressive event protocol을 이해하는 데 유효하다. React/Ink 영상의 핵심은 canonical state를 declarative terminal projection으로 만드는 데 유효하다.

그러나 generator만 보아서는 permission·durability를 설명할 수 없고, UI만 보아서는 effect semantics를 설명할 수 없다. 이 프로젝트에서 둘은 QueryEngine과 REPL/SDK adapter 사이를 이어 주는 메커니즘이다.

스터디 자료는 영상을 chapter 기준으로 승격하지 않고 실제 source path 안에 배치한다. 따라서 영상의 직관을 얻은 뒤 반드시 event identity, state ownership, failure path로 돌아온다.

코드 뒤에서 작동하는 언어·런타임 메커니즘

문법 이름을 외우기보다, 런타임이 실제로 무엇을 저장하고 언제 제어를 넘기는지와 이 프로젝트가 그것을 어떤 책임에 사용하는지를 함께 본다.

React render/commit

언어가 제공하는 것
component를 순수 계산으로 호출한 뒤 변경분만 host renderer에 commit한다.
이 저장소가 쓰는 방식
Ink가 terminal 화면을 state의 projection으로 갱신한다.
놓치기 쉬운 함정
render 중 process/tool effect를 실행하면 재호출 때 중복될 수 있다.

context provider

언어가 제공하는 것
component subtree에 value를 전달하고 value identity 변화로 consumer render를 유발한다.
이 저장소가 쓰는 방식
modal, queue, notifications, overlay state를 공유한다.
놓치기 쉬운 함정
넓은 mutable value는 ownership과 rerender 범위를 과도하게 넓힌다.

async iterator protocol

언어가 제공하는 것
host가 next/return/throw를 호출해 producer와 양방향 종료 의미를 만든다.
이 저장소가 쓰는 방식
SDK caller가 engine event를 점진적으로 소비한다.
놓치기 쉬운 함정
network bridge의 queue와 durable resume는 iterator가 자동 제공하지 않는다.

runtime validation schema

언어가 제공하는 것
wire message를 parse해 control union을 좁힌다.
이 저장소가 쓰는 방식
SDK/remote의 permission·interrupt·configuration message를 검증한다.
놓치기 쉬운 함정
schema version과 late response correlation이 없으면 올바른 모양의 잘못된 응답이 된다.

adapter normalization

언어가 제공하는 것
외부 protocol의 이름·schema·result를 내부 contract로 변환한다.
이 저장소가 쓰는 방식
MCP tool과 resource를 Tool registry와 message system에 연결한다.
놓치기 쉬운 함정
연결 성공을 authority나 trust로 승격하면 안 된다.

child runtime isolation

언어가 제공하는 것
별도 context, budget, tool set, cancellation을 가진 중첩 실행을 만든다.
이 저장소가 쓰는 방식
AgentTool과 Task가 subagent/background work를 관리한다.
놓치기 쉬운 함정
workspace effect와 결과 merge까지 자동 격리되는 것은 아니다.

같은 turn을 REPL과 SDK에서 비교하기

core event는 같고 projection과 control 방식만 달라지는지, 실제 코드의 타입과 state owner로 확인한다.

  1. partial assistant message, permission request, tool progress, final result 네 사건을 고른다.
  2. 각 사건이 QueryEngine에서 어떤 SDKMessage가 되고 REPL에서 어떤 state update와 component가 되는지 찾는다.
  3. consumer가 느리거나 disconnect된 경우 event delivery와 engine 실행이 어떻게 달라지는지 적는다.
  4. MCP tool 하나를 골라 discovery → registry → permission → result normalization을 추적한다.
  5. AgentTool child task 하나를 parent session의 canonical state와 UI projection으로 나누어 그린다.
완료의 기준UI, SDK, remote가 별도 제품 로직이 아니라 core protocol의 서로 다른 adapter/projection이며 각자 고유 실패를 가진다고 설명할 수 있으면 된다.
