1. 보고서의 목적과 읽기 계약

독자 질문. 고정된 비공식 구현 스냅샷과 상관된 2차 자료는 무엇을 증명할 수 있고, 독자는 이를 어떻게 재구성해 설명할 수 있는가?

먼저 답하면: 이 보고서는 정확히 고정된 두 리비전과 독립 검토를 거친 후보만을 학습 가능한 구조로 재표현한다. 현재 Claude Code의 공식 동작, 설계 의도, 런타임 신뢰성, 성능, 보안 효과를 설명하는 제품 문서가 아니다. 또한 원고 작성은 보고서 수락·출판·정산이 아니다.

주 독자는 TypeScript와 비동기 프로그래밍을 알고, 터미널 UI·도구 호출·대화 연속성의 내부 구조를 근거와 함께 이해하려는 기술 독자다. 2차 독자는 주장 강도, 출처 상관성, 실패·보안 한계를 검토하려는 리뷰어다. 독자는 읽은 뒤 세 도메인의 소유 경계를 구분하고, 한 개의 제한된 추적을 정확한 앵커에서 재구성하며, 자격부여·기각·보류·미확인을 더 강한 표현으로 바꾸지 않아야 한다.

범위와 비범위

  • 범위: D1 터미널 입력·상태·렌더 투영, D2-r2 비동기 턴·권한·도구 실행·결과, D3-r2 컨텍스트·기록·압축·재개 표현.
  • 비범위: 현재 공식 제품의 실제 배포 동작, 의도, 벤치마크, 개인정보 보호 효과, crash durability, 외부 효과 rollback·settlement.
  • 학습 상한: 연습은 제공하지만 실시하지 않았다. 독자의 이해·전이·준비도·역량 주장은 없다.
  • 산출물 상한: 이 HTML은 독립 원고 검토 전 후보이며, PDF를 렌더하거나 출판하지 않았다.

4. 필요한 만큼만 배우는 전제 지식

독자 질문. 뒤의 메커니즘을 이해하려면 무엇을 먼저 구분해야 하는가?

먼저 답하면: TypeScript/Node 자료형, async iteration의 yield와 return, React/Ink의 prop 투영, tool protocol, availability와 authority, 컨텍스트와 저장을 구분하면 충분하다. 이 primer는 준비도 평가가 아니라 뒤 장의 정확한 용어 다리다.

1) TypeScript 자료형과 소유권

type과 discriminated union은 메시지나 이벤트의 가능한 모양을 표현한다. 자료형에 필드가 있다는 사실은 그 값을 만드는 owner, 실행 권한, 외부 효과를 증명하지 않는다. 예를 들어 tool_use block이 API에 보인다는 것은 요청 가능성을 뜻할 뿐 실행 허가는 아니다.

2) async generator: yield와 return

async generator는 여러 중간 값을 yield하고 마지막 내부 값을 return할 수 있다. for await 소비자는 yielded message를 관찰하지만 내부 Terminal을 같은 방식으로 받지 않는다. D2의 query()는 yield*로 내부 terminal을 보존하고, 외부 QueryEngine은 수집된 메시지로 별도 결과를 만든다.

3) React/Ink와 렌더 투영

React component가 props를 받아 subtree를 계산하는 것은 투영이다. 그 component가 conversation state를 소유하거나 terminal bytes를 쓴다는 뜻은 아니다. D1의 Messages는 정규화·filter·group·slice·row 생성을 담당하지만 upstream producer와 terminal paint는 admitted 범위 밖이다.

4) 도구 프로토콜과 ID pairing

assistant의 {type:'tool_use', id, name, input}에는 같은 ID를 가진 user {type:'tool_result', tool_use_id:id, content, is_error?}가 대응한다. 이 matching ID와 assistant-before-result 순서가 다음 모델 요청 전에 지켜야 할 핵심 invariant다.

5) availability, authority, execution

availability는 모델에 도구 schema가 보이는 상태다. authority는 hook, rule, canUseTool, context handler가 허용·거부·질문·safety 결정을 내리는 경계다. execution은 validation 뒤 실제 tool.call로 들어가는 별도 단계다.

6) context, transcript, compaction, resume

request context는 모델 입력용 파생 투영이지 저장소가 아니다. live Message[]는 process-owned이고, JSONL은 별도 append-oriented 기록이다. compaction은 오래된 model-visible content를 boundary와 생성된 summary로 바꾸는 손실 변환이며, resume는 chain과 선택 상태를 재구성하지 byte-for-byte replay하지 않는다.

5. 주장·앵커·검토 상태를 결합하는 분석법

독자 질문. 한 문장을 보고서에 넣을 수 있는지 어떻게 판정하는가?

먼저 답하면: 정확한 리비전 → path와 symbol/range → candidate evidence class → 독립 review state → 인접 qualification → claim ceiling 순으로 결합한다. 어느 한 단계도 뒤 단계를 대신하지 않으며, 저자는 누락된 join을 새 연구나 claim repair로 채우지 않는다.

  1. 주장 원자화: 정적 존재, 공개 계약, 실행 관찰, 의도, 성능, 보안 효과를 한 문장에 섞지 않는다.
  2. 버전 고정: primary 2ca5…, secondary f4d6… 외의 branch/current 상태를 끌어오지 않는다.
  3. 앵커 결합: commit, path, symbol/range, applicability를 claim ID에 붙인다.
  4. 출처군 판정: secondary의 두 표기는 하나의 non-independent family로 계산한다.
  5. 검토 상태 적용: verified만 무조건 강한 말이 되는 것이 아니다. qualified는 limitation과 함께, rejected는 반증으로만, held는 gap으로만 쓴다.
  6. 교차 edge 중지: endpoint가 각각 verified여도 integration edge가 qualified/held면 그 상태를 유지한다.
  7. 반증 가능성: verdict를 바꿀 증거—admitted runtime trace, exact consumer edge, qualified transcript, durability receipt 등—를 미확인으로 남긴다.

D3-r2. 컨텍스트·기록·compaction·resume

질문. context, transcript, compaction, resume 표현은 owner·lifetime·persistence에 따라 어떻게 다른가?

제한된 답: request context는 model-input projection, live Message[]는 process state, local JSONL은 append-oriented event log, remote history는 remote-defined event source, compaction summary는 손실 파생물, snapshot은 event-backed reconstruction input, session memory와 MEMORY.md는 서로 다른 memory-like source다. resume는 chain과 선택 상태를 재구성할 뿐 원본 replay가 아니다.

표현과 변환 trace

  1. query entrypoint는 system prompt, user/system context, tools, 선택된 messages로 request context를 조립한다. 이는 저장소가 아니다.
  2. live messages는 main/fork loop가 소유하고 cache edit·result clearing·compaction replacement로 바뀔 수 있다. transcript recording은 별도 path다.
  3. local JSONL은 uuid/parentUuid message chain과 metadata/snapshot entry kind를 기록한다. queued/비대기 append와 별도 flush가 보이므로 crash durability는 미확인이다.
  4. compaction은 summarize할 범위를 고르고 boundary, summary, optional kept messages, bounded attachments, hook result 순으로 새 context shape를 만든다. summary·attachments는 생성되고 kept messages는 relink될 수 있다.
  5. resume는 chain walk, named repair, snapshot 선택, bounded file restoration을 통해 메시지와 AppState 일부를 재구성한다. cycle/dangling parent에서는 partial chain이 될 수 있다.

9. 실패·복구·보안 경계

독자 질문. 보이는 방어·복구 메커니즘은 어떤 효과를 보장하고 무엇을 보장하지 않는가?

먼저 답하면: 세 도메인에는 guard, error result, pairing synthesis, bounded restoration, failure breaker, mode/switch 같은 메커니즘이 있다. 그러나 mechanism의 존재는 외부 effect rollback, crash durability, privacy effectiveness, cleanup settlement를 증명하지 않는다.

D1: 입력·렌더 실패

  • Guard: footer/selection/suggestion 상태는 unintended submit을 막는다. guard가 통과한 뒤 callback effect는 injected owner에 달렸다.
  • Queue edit: Escape로 queued content를 input-local state에 복원할 수 있다. queue 생성·ordering·drain·persistence·execution reconciliation은 D1 밖이다.
  • Cancellation: idle speculation abort와 headless QueryEngine abort method는 각각 보인다. 두 메커니즘을 interactive cancellation cascade로 연결하지 않는다.
  • Render failure: handler exception log, unsupported block null, local Suspense fallback은 보인다. whole-tree ErrorBoundary·repaint recovery는 미확인이다.
  • 보안: input routing과 local state boundary는 보이지만 model/tool authority 또는 production security를 소유하지 않는다.

D2-r2: 권한·도구·cleanup 실패

  • Unknown tool/invalid input/denial: silently drop하지 않고 error tool_result를 만들 수 있다. ordinary denial은 continuation 가능성이 있고 abort/preventContinuation은 현재 턴을 멈춘다.
  • Sibling failure: executor는 completed/remaining result를 회수하고 missing/aborted result를 합성해 pairing invariant를 지키려 한다.
  • Fallback: partial assistant message tombstone, old result state clear, executor discard/replace가 보인다. 이미 시작된 external effect의 원상복구는 아니다.
  • Hook: PreToolUse·PermissionRequest·PostToolUse/Failure·Stop의 위치가 다르다. hook allow는 deny/ask/safety를 우회하지 않는다.
  • Settlement: feature-gated cleanup exception이 swallowed일 수 있으므로 resource release와 external settlement는 미확인이다.

D3-r2: 기록·chain·compaction·privacy 실패

  • Threshold: estimation/env/model/gate가 trigger를 바꾼다. static condition은 provider token truth나 successful compaction을 보장하지 않는다.
  • Partial write: append queue와 flush separation은 보이지만 fsync·transaction·checksum·parse receipt이 없다. crash 후 완전성을 주장하지 않는다.
  • Malformed tombstone: 큰 파일 slow path skip, malformed line keep, error ignore가 있을 수 있다. load failure는 empty map/no messages가 될 수 있다.
  • Malformed chain: cycle은 partial chain, dangling parent는 walk stop을 만들며 named repair만 보인다.
  • Compaction failure: prompt-too-long retry는 과거 round를 버릴 수 있고, no-summary/API/incomplete error는 throw한다. auto-compact는 false를 반환하고 연속 실패 뒤 멈출 수 있다.
  • Restoration: file generation은 bounded/fallible이며 missing worktree·unavailable agent에 fallback이 있다. 완전한 재생이 아니다.
  • Privacy: requested file modes, disable switches, authenticated seam은 공격면을 줄이는 메커니즘일 수 있으나 encryption·retention·secure deletion·redaction·remote policy 효과를 입증하지 않는다.

효과 주장의 중지 조건

“검사한다”를 “안전하다”로, “append한다”를 “crash-safe하다”로, “mode를 요청한다”를 “privacy-effective하다”로, “discard한다”를 “rollback한다”로 바꾸지 않는다. 그런 승격에는 별도 runtime environment, exact input/output, effect receipt, failure injection, external resource reconciliation이 필요하다.

12. 용어집

독자 질문. 비슷해 보이는 용어의 owner·effect·lifetime은 어떻게 다른가?

먼저 답하면: context, transcript, session, summary, memory-like facility를 한 저장소로 합치지 않고 availability, authority, execution, validation, acceptance, publication, settlement를 서로 다른 lifecycle fact로 유지해야 한다.

Acceptance(수락)
정해진 owner가 후보를 받아들이는 별도 결정. validation이나 checker pass와 다르다.
Async generator
여러 yielded value와 별도 final return을 갖는 비동기 반복기.
Authority(권한)
작업이 허용되는지를 결정하는 hook/rule/canUseTool/handler 경계. availability와 다르다.
Availability(가용성)
도구 schema나 capability가 요청 가능한 표면에 존재하는 상태. 실행 허가가 아니다.
Compaction
오래된 model-visible content 일부를 boundary·생성 summary·kept messages·attachments 등으로 바꾸는 손실 변환.
Context
한 model request에 선택되어 들어가는 system/user/tool/message 투영. 저장소 자체가 아니다.
Correlated secondary
같은 reconstruction lineage와 상관될 수 있는 귀속 2차 자료. 독립 구현 corroboration이 아니다.
Crash durability
process/system failure 뒤 기록이 약속된 형태로 남는 성질. append/flush code만으로 증명되지 않는다.
Elided excerpt
원문 일부를 검색 가능한 text로 보이되 omission marker로 생략을 표시한 excerpt. 전체 exact block이나 pseudocode가 아니다.
Execution(실행)
권한 판정 뒤 실제 call과 effect가 일어나는 단계.
Held(보류)
현재 admitted evidence로 해소할 수 없어 support로 쓰지 않는 claim/edge 상태.
JSONL
한 줄에 한 JSON entry를 두는 append-oriented 기록 형식. 여기서는 message chain 외 metadata/snapshot kind도 포함한다.
Memory-like facility
session memory나 MEMORY.md처럼 기억에 쓰이지만 owner·lifetime·persistence가 transcript와 다른 입력원.
Publication(출판)
accepted digest를 외부/shared target에 노출하는 별도 effect. 원고 작성과 다르다.
Qualified(자격부여)
명시된 limitation과 인접하게 사용할 수 있는 검토 상태.
Render projection
props/state에서 UI subtree를 계산하는 과정. upstream state ownership이나 terminal paint를 뜻하지 않는다.
Resume
기록 chain과 선택 상태를 재구성하는 과정. byte-for-byte replay가 아니다.
Rollback
이미 발생한 effect를 transaction 수준에서 되돌리는 보장. discard/result reconciliation과 다르다.
Session
conversation·recording·remote lifecycle을 묶는 식별/수명 단위. live state나 한 request context와 동일하지 않다.
Settlement(정산)
파일·claim·resource·assignment 등 모든 열린 항목에 terminal disposition을 부여하는 별도 lifecycle 단계.
Summary
선택된 과거 내용을 압축해 생성한 파생 message. 원문과 semantic/byte equivalence를 주장하지 않는다.
Transcript
session event를 기록하는 별도 persistence path. live Message[]나 request context와 다르다.
Validation(검증)
정해진 candidate와 기준에 대한 판정. acceptance·publication·settlement 권한을 만들지 않는다.
