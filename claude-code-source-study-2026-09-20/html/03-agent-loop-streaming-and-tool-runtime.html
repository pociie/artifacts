ITERATION04

한 번의 while(true) 해부

각 iteration은 “입력 projection → request → stream → tool → enrichment → next state”의 transaction-like 경계를 만든다.

  1. 현재 State를 iteration-local 변수로 펼친다.
  2. memory/skill prefetch를 시작해 model/tool 시간과 겹친다.
  3. snip·microcompact·context collapse·autocompact로 messages projection을 만든다.
  4. token blocking 조건을 확인한다.
  5. model stream을 소비하며 event를 yield하고 tool_use를 수집한다.
  6. recoverable error면 표시를 보류하고 recovery branch를 평가한다.
  7. tool이 없으면 stop hook/budget을 확인하고 terminal return한다.
  8. tool batch를 실행하고 result/attachment/context update를 모은다.
  9. max turn을 확인하고 next State를 만든 뒤 continue한다.

TOOL DETECTION09

stop_reason만 믿지 않는다

소스 주석은 API의 stop_reason === tool_use가 항상 신뢰할 수 없다고 밝히고, 실제 stream에서 tool_use block을 관찰한 사실을 loop continuation 신호로 쓴다.

이 설계는 “summary metadata”보다 “실제 payload evidence”를 우선한다. 분산·스트리밍 시스템에서 상태 플래그보다 관찰된 event를 기준으로 전이하는 전형적인 방어다.

FOLLOW-UP13

INVARIANTS17

코드에서 추출한 핵심 불변식

함수 흐름보다 불변식을 적어야 테스트와 재구현에 사용할 수 있다.

□ 모든 tool_use id에는 정확히 대응하는 tool_result 또는 명시적 interruption이 있어야 한다.
□ fallback 전 partial assistant projection은 새 stream과 공존하지 않는다.
□ API로 재전송할 original message는 observer용 backfill 때문에 mutate되지 않는다.
□ permission/validation을 통과하지 않은 tool effect는 실행되지 않는다.
□ concurrency-unsafe tool의 context modifier는 직렬 순서로 적용된다.
□ recoverable error는 recovery가 불가능하다고 결정되기 전 외부 terminal로 누출되지 않는다.
□ max-turn·token-budget·recovery retry에는 상한이 있다.
□ abort는 rollback이 아니므로 부분 효과를 별도로 정리한다.
