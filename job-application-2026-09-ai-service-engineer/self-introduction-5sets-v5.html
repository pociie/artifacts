3. 지원 직무와 도메인 이해

DOMAIN MODEL

공식 공고에서 직접 확인한 AI 서비스 엔지니어의 업무는 모델 연구만이 아니라 API·백엔드, 데이터 파이프라인, 플랫폼 운영·고도화, 서비스 발굴·검증, 튜닝·품질 검증을 함께 다루는 서비스 전달 역할입니다.

4. collab-mono와 Loop Architecture 경험의 표현

PROJECT ABSTRACTION

저수준 모듈이나 실행 메커니즘을 나열하지 않고, 저장소와 설계 문서가 보여주는 의미를 사람의 업무 흐름으로 추상화했습니다. 이 방식은 기술을 숨기는 것이 아니라 기술이 어떤 책임과 확인을 가능하게 했는지를 중심에 두는 방식입니다.

목표 정의

사람이 이루려는 업무 결과

맥락 구조화

정보·제약·책임·확인 기준

처리 설계

서비스가 이어지는 흐름

검토 상태

결과·기록·오류 확인

재평가

변경·피드백을 다음 설계로

내부 설계 개념보편적 의미자소서에 반영한 문장
execution routing작업의 목표·제약·미확인을 정리해 적절한 처리 경로를 선택하는 설계작업 맥락과 책임을 먼저 정리한 뒤 처리 경로를 설계했습니다.
reusable artifact lifecycle재사용 가능한 설계·검증 자료를 목적과 범위에 맞게 관리하는 방식다음 판단에 쓸 수 있도록 설계 자료와 확인 기준을 정리했습니다.
knowledge/context projection목적에 필요한 정보와 제약을 선별해 처리에 사용할 수 있는 맥락으로 구성하는 과정모호한 요구를 필요한 정보·제약·확인 기준으로 구조화했습니다.
workflow/verification/adaptive review처리와 검증을 분리하고 변경이 생기면 다음 확인 기준을 다시 세우는 순환결과 확인과 변경 후 재검토를 설계의 일부로 두었습니다.

프로젝트 규모

28개 npm workspace는 넓은 저장소 범위의 근거로만 사용했습니다. 이를 팀·서비스·사용자·트래픽 규모로 확대하지 않았습니다.

개인 역할

요구 분석·구조 설계·구현·검증·배포 구성을 연결했다는 사용자 설명을 사용했습니다. 실제 변경 파일·명령·시점은 제출 전 확인 대상입니다.

완수의 기준

기능 수가 아니라 사용자 목표가 결과 확인까지 이어지고, 오류를 다시 확인해 다음 개선에 쓸 수 있는 상태로 정의했습니다.

표현하지 않은 것

report-only, authorityEffect:none, 준비 조건, 개발 smoke/loopback 등을 운영 성과·승인·품질 보장으로 표현하지 않았습니다.

0~4 공통 anchor

90점의 의미

현재 공고·문항·근거 스냅샷에서의 편집 후보 기준입니다. 역량 인증, 제출 승인, 합격 확률, 프로젝트 운영 성과로 해석하지 않습니다.

보호 게이트

300~700자, 문항 필수요소, 근거 귀속, 성과 과장 방지, 문항 경계, 상위 추상화, 공통 용어, 주장 추적성, 사용자 경계를 확인합니다.
